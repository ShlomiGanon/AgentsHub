# דוח בדיקה מקיף: אבטחת מידע, API ובדיקות QA

מסמך זה מרכז את ממצאי הבדיקה המקיפה שבוצעה בקוד המערכת (AgentsHub), בחלוקה לפי רמות חומרה ותחומים.

---

## 1. פרצות וסיכוני אבטחה (Security Vulnerabilities)

### 1.1 אימות זהות פגיע לחלוטין באמצעות Header גלוי ללא Token/חתימה (Authentication Bypass / Spoofing)
* **מיקום:** `api/request_boundary.py` (שורות 77–88)
* **תיאור הבעיה:** הפונקציה `authenticate()` קוראת את ה-Header בשם `X-Identity` ומבצעת בדיקה האם המשתמש קיים במסד הנתונים. **אין שימוש בסיסמה, JWT, API Key, חתימה קריפטוגרפית או Session.**
* **השלכה:** כל גורם שיכול לגשת לפורט ה-API יכול לשלוח `X-Identity: <commander_id>` ולהתחזות למפקד בעל הרשאות מלאות לביצוע פעולות, אישור פרוטוקולים ושינוי הגדרות מערכת.
* **המלצה:** להוסיף מנגנון Bearer Token / API Key / HMAC סודי בין רכיב ה-Bot/Clients לבין ה-API.

---

### 1.2 התחזות שולח (Sender Spoofing) בשליחת הודעות ואירועים
* **מיקום:** `api/routes.py` (בנתיבים `/Event` ו-`/Msg`)
* **תיאור הבעיה:** בנתיבים אלו האימות מתבצע מול ה-`X-Identity`, אך השדה `sender_identity` נלקח ישירות מגוף הבקשה (JSON payload) ונשמר ב-DB ללא אימות שהוא תואם לזהות המאומתת.
* **השלכה:** משתמש מורשה (למשל צופה – Viewer) יכול לשלוח דיווח או בקשה בשמו של משתמש אחר או מפקד.
* **המלצה:** לאכוף ש-`sender_identity` חייב להיות זהה ל-`caller_identity` (אלא אם הקורא הוא ה-`bot-service` המורשה לפעול כ-Proxy).

---

### 1.3 שינוי קוד מקור פייתון בזמן ריצה (Dynamic Code Rewriting / Injection Risk)
* **מיקום:** `protocols/repository.py` (הפונקציה `_write_protocols`)
* **תיאור הבעיה:** הפונקציה `_write_protocols()` מבצעת כתיבה מחדש לקובץ ה-Python (`.py`) של הפרופיל בדיסק על ידי יצירת מחרוזות קוד והחלפת מקטע ה-AST.
* **השלכה:**
  1. סיכון של Code Injection / קריסת סינטקס אם מועבר תוכן לא סטנדרטי.
  2. בסביבות ענן / Docker שבהן מערכת הקבצים לקריאה בלבד (Read-Only Container), ה-API יקרוס עם שגיאת `PermissionError`.
* **המלצה:** לשמור פרוטוקולים דינמיים במסד הנתונים (SQLite) במקום לערוך קובצי קוד מקור של פייתון בזמן ריצה.

---

### 1.4 היעדר הגבלת גודל הודעה (DoS / Prompt Injection / חריגת תקציב LLM)
* **מיקום:** `api/routes.py` (בקבלת הודעות ב-`/Msg` ו-`/Event`)
* **תיאור הבעיה:** שדה ה-`text` ב-`/Msg` ו-`/Event` אינו מוגבל באורך (בשונה מ-`conversation_id` שמוגבל ל-200 תווים).
* **השלכה:** שליחת טקסט ענק תועבר ישירות ל-LLM, תנפח עלויות API, תגרום ל-Timeouts ותתקע את תור ה-Agents (`_provider_semaphore`).
* **המלצה:** להגדיר מגבלת תווים קשיחה לשדה `text` (למשל עד 4,000 תווים).

---

## 2. בעיות בשכבת ה-API והתקשורת (API & Transport Issues)

### 2.1 חריגה ממגבלת 64 בתים ב-Telegram Inline Keyboard Callbacks
* **מיקום:** `bot/interactions.py` (בפונקציות `build_callback_data` ו-`build_clarification_callback_data`)
* **תיאור הבעיה:** המבנה `approve:<event_id>:<choice>` ו-`clarify:<event_id>:<classification>` משרשר מזהה אירוע ושם פרוטוקול/סיווג.
* **השלכה:** טלגרם מגבילה כפתורי `callback_data` ל-**64 בתים בלבד**. אם מזהה האירוע ושם הפרוטוקול ארוכים, שליחת ההודעה תיכשל מצד טלגרם בשגיאת `BUTTON_DATA_INVALID`, והמפקד לא יקבל את הבקשה לאישור.
* **המלצה:** להשתמש ב-`hold_id` קצר או מפתח מקוצר (short hash) במקום לשרשר שמות ארוכים.

---

### 2.2 קריסת 500 ב-`GET /Notifications` כתוצאה מ-Event חסר (Error Cascade)
* **מיקום:** `api/routes.py` (שורות 1016–1046)
* **תיאור הבעיה:** הפונקציות `_job_payload`, `_target_chat_ids` ו-`_precedent_closure_payload` קוראות ל-`fetch_event(event_id)` ומשתמשות ישירות בתוצאה: `event["outcome"]` או `event["sender_identity"]` מבלי לוודא ש-`event is not None`.
* **השלכה:** אם נרשמה התראה על אירוע שנדחה, נמחק או שלא נמצא, ה-API מחזיר שגיאת `500 Internal Error`. כתוצאה מכך, לולאת הפולינג של הבוט (`run_notification_poll_loop`) נכנסת לרצף כשלונות ואינה מצליחה להתקדם ב-Cursor.
* **המלצה:** להוסיף בדיקות `if event is None:` בכל בוני ה-Payloads של ההתראות.

---

### 2.3 חוסר סנכרון בין שינוי פרוטוקול לזיכרון הריצה (Desynchronization)
* **מיקום:** `api/routes.py` (בנתיבי `/Protocol`)
* **תיאור הבעיה:** בעת קריאה ל-`POST/PUT/DELETE /Protocol`, הקובץ בדיסק מעודכן, אך אובייקט ה-`ctx.deps.protocol_set` שנטען בזיכרון בזמן עליית השרת אינו מתרענן.
* **השלכה:** המשתמש מקבל הודעת הצלחה, אך השרת שממשיך לרוץ לא מכיר בפרוטוקול החדש/המעודכן עד להפעלה מחדש (Restart).

---

## 3. בעיות Concurrency, נעילות ושלמות נתונים (Concurrency & Architecture)

### 3.1 נעילת בוט תקועה לאחר קריסה (Stale SingleInstanceLock Deadlock)
* **מיקום:** `bot/background_services.py` (במחלקה `SingleInstanceLock`)
* **תיאור הבעיה:** מנגנון ה-`SingleInstanceLock` יוצר קובץ נעילה עם `os.O_CREAT | os.O_EXCL`. אם התהליך נסגר בפתאומיות (Kill, הפסקת חשמל, קריסת חומרה), הקובץ נשאר בדיסק.
* **השלכה:** בניסיון הפעלה חוזר, הבוט יסרב לעלות עם שגיאת `AlreadyRunningError` עד שמישהו ימחק ידנית את הקובץ.
* **המלצה:** לבדוק האם ה-PID הרשום בקובץ באמת קיים במערכת ההפעלה, או להשתמש בנעילת קבצים ברמת OS (`msvcrt.locking` ב-Windows / `fcntl.flock` ב-Linux).

---

### 3.2 היעדר ניקוי וניהול זיכרון ב-`_tool_class_cache`
* **מיקום:** `agents/runtime.py`
* **תיאור הבעיה:** המילון `_tool_class_cache` שומר מחלקות דינמיות (`type(...)`) שנוצרות עבור CrewAI ללא מנגנון פינוי (Eviction/LRU/WeakRef).
* **השלכה:** במערכת פעילה לאורך זמן או בטעינה מחדש של סוכנים, הזיכרון עלול לגדול בהתמדה (Memory Leak).

---

## 4. בדיקות QA, מקרי קצה וחוסן קוד (QA & Robustness)

### 4.1 חוסר עקביות בהיסטוריית שיחה במקרה של כשל בעיבוד (Uneven Conversation History)
* **מיקום:** `api/routes.py`
* **תיאור הבעיה:** הודעת המשתמש נשמרת בהיסטוריית השיחה (`_remember("user", text)`) מיד עם קבלת הבקשה. אם בהמשך מתרחש כשל (כגון שגיאת מודל או Timeout), אין שמירה של הודעת שגיאה מתאימה מצד ה-Assistant.
* **השלכה:** רצף השיחה נשאר מקוטע (שתי הודעות משתמש רצופות ללא מענה), דבר שעלול לבלבל את ה-LLM בבקשות הבאות באותה שיחה.

---

### 4.2 טיפול ב-Race Condition באישור/הבהרת Holds
* **מיקום:** `api/routes.py` (בנתיבי `/Clarify` ו-`/Approve`)
* **תיאור הבעיה:** אם שני מפקדים עונים על אותו Hold בו-זמנית, הראשון פותר את ה-Hold והשני מקבל שגיאת `InvalidInputError` (קוד 400) במקום `ConflictError` (קוד 409) או `NotFoundError` (קוד 404).
