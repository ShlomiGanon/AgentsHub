# AgentsHub — Regression Check: Required-Fields Gate Didn't Ask for Location on a Fire Report

**Headline finding: this is (b), not (c) or (e).** The required-fields
gate itself is not broken — it never had anything to enforce, because
`profiles/demo.py` (the deployed profile) never declares `area` (or any
field) as required for `"fire"`. The gate mechanism built and tested in
`REQUIRED_FIELDS_AND_CLOSED_DECISIONS.md` Part 1 is a real, working,
opt-in mechanism; nobody ever configured `demo.py` to opt `"fire"` into
it. Separately, and more importantly per the user's severity framing:
**dispatch was still attempted with a known-missing location**, entirely
independent of the required-fields mechanism — this is the standalone
safety question flagged at the end of this document, not fixed here.

**Method:** live reproduction, real model calls (openrouter/claude-sonnet-4.6),
against an isolated scratch SQLite DB (`area_field_repro.db`, under this
session's scratchpad directory — never production data), running
`profiles.demo` with its `DB_PATH` monkeypatched before load. Two scripted
runs: (1) the report + immediate "what's the last event" follow-up: (2) a
commander approving the resulting flagged-protocol hold, then re-asking
"what's the last event." Full logs captured and quoted below, not
paraphrased.

---

## Step 0 — the dispatch-without-location sequence, precisely

1. **Report sent, no location.** `POST /Msg` with `"אני רוצה לדווח על
   שריפה"` → `202`, `{"taken_as": "report", "event_id": "bf7ac1512db4498a9b0d0ef8e60182c6"}`.
2. **The required-fields gate never ran — not "ran but didn't block."**
   The captured log, in order, immediately after extraction:
   ```
   extraction → fire/(no area), missing: area, severity, occurred_at, entities
   [risk_assessment stage] ...
   risk assessed → high (score=0.6, ...)
   [protocol_selection stage] ...
   protocol selected → dispatch_response (...)
   precedent lookup → 0 match(es), not closed
   approval hold created → reason: flagged_protocol
   ```
   There is no `hold_created`/`event_data` log line anywhere, and
   `list_held_events("event_data")` returned `[]` after this run. Risk
   assessment ran in the very next stage after extraction — nothing sat
   between them. This is the mechanical proof it's (b): `_apply_required_fields_gate`
   (`orchestrator/flows.py`) *is* called unconditionally for every report,
   but its first line — `required = deps.event_type_registry.required_fields_for(classification); if not required: return None`
   — returned `None` immediately, because `required_fields_for("fire")`
   is empty for this profile. There was nothing to detect and nothing to
   enforce, not a detection that got ignored.
3. **The "what's the last event" answer is honest about the gap — this
   part works correctly.** After step 1 alone (protocol flagged for
   approval, not yet executed), the answer explicitly named the event,
   its risk, and that it was "held for commander approval" — it did not
   claim a location or an outcome that hadn't happened yet. After a
   commander approved the hold and the protocol actually ran (see below),
   the answer explicitly and correctly reported: outcome **failed**, and
   that the reference agent "checked whether a fallback area exists — none
   does — refused to fabricate one, and flagged the event for manual
   triage." The read/display side never overclaimed.

**One clarification on "forces sent":** in this specific reproduction,
the executed step (`reference_agent`, model-driven) recognized the missing
location itself — its task text (generated by `task_formulation`, a live
model call) happened to explicitly instruct it to check for a fallback
area and refuse to fabricate one if none existed, and it did exactly
that; the run's final outcome was `"failed"`, not a completed dispatch.
No resources were actually "sent" in this run. This does **not** mean the
underlying concern is unfounded — see "Standalone safety concern" below:
this self-correction was the model's own judgment call this one time,
with no code-level backstop requiring it. A differently-phrased task (an
entirely plausible outcome of the same model on a different sampling, or
a different profile's protocol/task wording) could just as easily have
proceeded to report a completed dispatch against no known location, and
nothing in the current code would have stopped it.

## Step 2 — Which of (a)/(b)/(c)/(d)/(e) actually happened

- **(a) Wrong event type resolved — ruled out.** Intent classified
  cleanly as `report` (not `conversation`/`question`), and extraction
  resolved `classification: "fire"` — a real profile event type. The
  phrasing did work as an actual report, not just an announced intent.
  (A more minimal phrasing like `"יש שריפה"` was not additionally tested,
  since (a) is already conclusively ruled out by this same run reaching
  extraction, protocol selection, and an approval hold.)
- **(b) Event type resolved to "fire," but "fire" has no `area` declared
  as required — confirmed, this is what happened.** `profiles/demo.py`
  (the profile actually used, read directly, not inferred):
  ```python
  EVENT_TYPES = ["fire", "medical"]
  ```
  — and a full-file search confirms **no `EVENT_TYPE_REQUIRED_FIELDS`
  attribute exists anywhere in `profiles/demo.py`** (`grep -n
  "EVENT_TYPE_REQUIRED_FIELDS" profiles/demo.py` → no matches). Per
  `profiles/loader.py`'s `load_profile`, an absent
  `EVENT_TYPE_REQUIRED_FIELDS` defaults to `{}` (by design — backward
  compatible, per `REQUIRED_FIELDS_AND_CLOSED_DECISIONS.md` Part 1's own
  "flag back if any profile would break" clause, which this profile
  satisfies by declaring nothing rather than breaking). So
  `EventTypeRegistry.required_fields_for("fire")` returns `()` — an
  empty tuple — for this deployment. The gate is working exactly as
  designed; the profile simply never opted `"fire"` into it.
- **(c) / (e) Gate reached but didn't fire, or fired but didn't
  block — ruled out.** Confirmed by the trace in Step 0: there is no
  `hold_created` log entry of kind `event_data` anywhere in this run,
  and `_apply_required_fields_gate`'s own first line
  (`required = ...; if not required: return None`) is the entire
  explanation — it returned before doing anything that could be called
  "detection." This is meaningfully different from (e) (detected, not
  enforced): there was no detection to fail to enforce.
- **(d) Question was asked but not delivered — ruled out.** No
  clarification/event-data message was ever generated in the first
  place (per the held-events dump and the log), so there was nothing for
  a transport issue to swallow.

## Step 3 — Why didn't `REQUIRED_FIELDS_AND_CLOSED_DECISIONS.md` Part 1's own test suite catch this?

**Root cause of the test gap: every Part 1 regression test that exercised
the gate constructed its own `EventTypeRegistry` with required fields
explicitly declared for the test's purposes — none of them exercised
`profiles/demo.py`'s actual, real configuration, which declares none.**
Concretely, `tests/test_orchestrator_flows.py::test_required_fields_gate_asks_only_for_the_field_extraction_could_not_resolve`
and `::test_required_fields_gate_resumes_into_risk_assessment_once_resolved`
both build:
```python
gated_deps = replace(
    deps,
    event_type_registry=EventTypeRegistry(types=deps.event_type_registry.types, required_fields={"fire": ("area", "severity")}),
)
```
— i.e., they prove the **mechanism** works correctly *given* a
declaration, which is real and valuable, but they don't (and were never
asked to) prove that the **shipped profile** actually makes that
declaration for any of its real event types. `tests/test_profile_loading.py`'s
`EVENT_TYPE_REQUIRED_FIELDS` tests are similarly mechanism-only, using a
hand-built `SimpleNamespace`, never `profiles.demo` itself. No test
anywhere asserts anything about `profiles/demo.py`'s own
`EVENT_TYPE_REQUIRED_FIELDS` content (because, at the time, none was
expected to exist — Part 1's own scope was "add the mechanism," not
"turn it on for the demo profile's event types," and nothing in that
authorization asked for the latter).

This is a coverage gap in the sense that the deployed, real-world
behavior for the profile actually running (`profiles.demo`, per `.env`)
was never checked end-to-end against a message this close to a genuine
user report — but it is not a bug in the tests that exist; they tested
exactly the mechanism they were asked to test, correctly.

**Is this isolated to "fire," or structural across every event type?**
Structural, by construction, and expected: `EVENT_TYPE_REQUIRED_FIELDS`
is opt-in per profile per event type (deliberately, per Part 1's own
backward-compatibility requirement). **Every** event type in **every**
shipped profile currently has zero required fields declared —
`profiles/demo.py`'s `"medical"` has exactly the same gap as `"fire"`,
and `profiles/template.py`'s two example types likewise declare none.
This is not a bug to fix in the gate mechanism (which behaves exactly as
specified); it is a plain content/configuration decision nobody has made
yet for any shipped profile.

**No code or test changes were made in this pass** — this is a diagnosis
task per the request; a fix (declaring `EVENT_TYPE_REQUIRED_FIELDS =
{"fire": ["area"]}` in `profiles/demo.py`, and deciding whether other
event types/profiles need the same) is a one-line-per-type profile change
once the user confirms they want it, and was intentionally left undone
here per the request's explicit instruction not to silently fix (b).

## Standalone safety concern (per the request — reported, not fixed)

Independent of whether `area` is formally declared as a required field
for any given event type: **should protocol execution ever be allowed to
attempt dispatch for an event with no resolved area at all?** Today,
nothing in the code enforces this as a rule — it is left entirely to
whatever the task-formulation model happens to write into that step's
instructions, and to the executing agent's own judgment about whether to
proceed. In this reproduction, both happened to behave conservatively
(the formulated task explicitly asked the agent to check for a location
and refuse to fabricate one; the agent complied, and the run outcome was
correctly `"failed"`). Concretely observed in the same trace, this
"safety net" is not structural: the step that ran was recorded with
`"required_event_fields": ["classification"]` — the model-driven task
formulation did **not** itself declare `"area"` as a per-step required
field, even though its own task text reasoned extensively about the
missing location. Nothing prevented that same formulation from omitting
the location caveat in its task text entirely; had it done so, the
executing agent would have had no textual cue to check for one, and the
existing per-step `required_event_fields` mechanism (which *could* have
caught this deterministically) went unused for it by the model's own
non-deterministic choice.

This is exactly the class of question the request asked to be surfaced,
not resolved unilaterally: if the answer wanted is "never dispatch
without a resolved location, regardless of per-event-type
`EVENT_TYPE_REQUIRED_FIELDS` configuration," that is a different,
more fundamental gate than the required-fields mechanism — e.g. a
built-in, protocol-independent rule that any protocol whose
`approved_tools`/criticality implies a physical dispatch action requires
`area` before task formulation runs, not merely "if the profile happened
to declare it." That is new design work, not a bug fix, and is left for
the user to decide.
